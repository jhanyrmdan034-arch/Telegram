# ورود آزمایشی بدون OTP (فقط محیط توسعه)

هدف: ورود به اپ اندروید و آزمایش قابلیت‌های پیام‌رسان با **دو کاربر مستقل** روی بک‌اند اختصاصی،
بدون نیاز به ارسال پیامک. مسیر OTP حذف نشده و دست‌نخورده باقی مانده است.

---

## ۱. روش کار

```
اپ اندروید (فقط بیلد Debug)
   شماره را وارد می‌کنی:  10001  یا  10002
        │
        ▼
PlatformAuthInterceptor.tryDevLogin()          ← فقط اگر BuildVars.DEV_LOGIN_ENABLED
        │   (پیش از هر تماس OTP)
        ▼
POST /api/v1/auth/dev-login {account:"demo_alice"}
        │
        ▼
بک‌اند: فقط اگر DEV_LOGIN_ENABLED=true و environment ≠ production
        → کاربر آزمایشی با پرچم is_test_account
        → صدور جفت توکن عادی (همان TTL، همان ابطال، همان لاگ)
        ▼
TL_auth_authorization  ──►  همان مسیر onAuthSuccess خود اپ
        ▼
مستقیم وارد صفحهٔ اصلی می‌شوی (هیچ کد و صفحهٔ اضافه‌ای نیست)
```

- **بدون هیچ تغییر ظاهری**: همان صفحهٔ شمارهٔ فعلی؛ فقط یک عدد پنج‌رقمی به‌جای شماره تایپ می‌شود.
- اگر بیلد Release باشد یا سرور اجازه ندهد، همان عدد مثل یک شمارهٔ معمولی تلقی و مسیر عادی OTP
  طی می‌شود (هیچ مسیر پنهانی باز نمی‌شود).

## ۲. حساب‌های آزمایشی

| شناسه (ورودی اپ) | نام‌کاربری بک‌اند | نام نمایشی | توضیح |
|---|---|---|---|
| `10001` | `demo_alice` | Alice Demo | حساب تست A |
| `10002` | `demo_bob` | Bob Demo | حساب تست B |

هر دو در استارتاپ (وقتی فلگ روشن باشد) به‌صورت idempotent ساخته می‌شوند:
`app/devlogin.py::ensure_demo_accounts` — با `is_test_account = True`، رمز تصادفی ناشناخته
(بنابراین فقط از مسیر dev-login قابل ورود است) و شناسه/پروفایل مستقل.

ساخت دستی: `python -m app.cli seed-demo` (نیازمند `DEV_LOGIN_ENABLED=true`).

## ۳. فعال‌سازی

```bash
# سرور (فقط توسعه/تست)
export DEV_LOGIN_ENABLED=true
# اپ: BuildVars.DEV_LOGIN_ENABLED = BuildConfig.DEBUG  → فقط در بیلد Debug روشن است
```

## ۴. امنیت

| قاعده | پیاده‌سازی |
|---|---|
| فقط توسعه/تست | `dev_login_enabled(settings)` = فلگ روشن **و** محیط ≠ production |
| در Production خاموش | `validate_for_production()` با روشن بودن فلگ، خطا می‌دهد و اپ بالا نمی‌آید |
| مسیر عمومی بدون احراز هویت وجود ندارد | endpoint فقط با فلگ پاسخ می‌دهد؛ در غیر این صورت **۴۰۴** (نه ۴۰۳، تا وجود مسیر هم لو نرود) |
| فقط حساب‌های تست | `find_demo_user` فقط کاربرانی با `is_test_account = True` را برمی‌گرداند؛ `root` و کاربران واقعی ۴۰۴ می‌گیرند |
| توکن معتبر/محدود/قابل ابطال | همان `_issue_tokens` و همان جدول `sessions`؛ خروج و ابطال دستگاه کار می‌کند |
| جدایی از کاربران واقعی | ستون `users.is_test_account` + نام‌های `demo_*` + رخداد امنیتی `auth.dev_login` در لاگ |
| محدودیت نرخ | همان `login_limiter` روی `dev-login:<ip>` |

## ۵. آزمایش انجام‌شده (روی سرور زنده با `DEV_LOGIN_ENABLED=true`)

`python tools/android_demo_login_probe.py --server http://127.0.0.1:8000` → **۲۶ بررسی، همه موفق**:

1. ورود هر دو حساب بدون هیچ کدی؛ پروفایل‌ها مستقل (id و نام متفاوت).
2. حساب ناشناخته و حساب واقعی (`root`) رد می‌شوند (۴۰۴).
3. نشست، نشست عادی است: refresh کار می‌کند، در لیست دستگاه‌ها دیده می‌شود.
4. **تبادل پیام واقعی**: alice می‌فرستد → bob همان لحظه روی WebSocket دریافت می‌کند؛ bob پاسخ می‌دهد؛
   تاریخچه هر دو جهت را نشان می‌دهد.
5. **وضعیت آنلاین/آفلاین**: با باز بودن سوکت bob، alice او را «آنلاین» می‌بیند و پس از بستن سوکت «آفلاین».
6. **خوانده‌شدن**: شمارندهٔ خوانده‌نشده ۱ → پس از read receipt صفر.
7. **بازیابی نشست** پس از «اجرای مجدد» و باقی‌ماندن تاریخچه.

تست‌های خودکار بک‌اند: `tests/test_dev_login.py` — ۱۰ تست (شامل تبادل پیام دو حساب با WebSocket واقعی،
حضور، ابطال نشست، رد حساب‌های واقعی، ممنوعیت در production).

## ۶. محدودیت‌ها

- **APK ساخته نشد و ورود از داخل اپ انجام نشد**: در این محیط JDK/Android SDK نیست و workflow آماده‌شده
  هم به‌دلیل نبود مجوز `actions:write` قابل اجرا نبود. آنچه اثبات شده، همان توالی دقیق درخواست‌های
  اپ روی سرور واقعی است، نه اجرای اپ روی دستگاه.
- **تلگرام اصلی هنوز دادهٔ صفحهٔ اصلی را از MTProto می‌گیرد**؛ پس پس از این ورود، تا سیم‌کشی فاز ۳
  لیست دیالوگ‌ها در اپ خالی است. (تبادل پیام در سطح API و WebSocket واقعاً کار می‌کند.)
- ورود آزمایشی **فقط با بیلد Debug** و سرور با فلگ روشن کار می‌کند؛ روی بیلد Release بی‌اثر است.
