# فاز ۲ — اتصال صفحهٔ ورود (LoginActivity) به احراز هویت بک‌اند اختصاصی

تاریخ: ۲۰۲۶-۱۱-۰۴ · شاخه: `arena/76249c66-telegram` · وضعیت: **پیاده‌سازی شد و روی سرور زنده آزمایش شد؛ کامپایل APK در این محیط ممکن نیست.**

---

## ۱. راهبرد: یک درز (seam) در لایهٔ انتقال، نه یک صفحهٔ ورود جدید

`LoginActivity` ده‌هزار و ۳۶۸ خط است و کل جریان ورود (کشور، شماره، کد، ثبت‌نام، رمز دومرحله‌ای،
Firebase، پرداخت، بازیابی) با انیمیشن‌ها و اعتبارسنجی‌های خودش در آن پیاده شده است. به‌جای دست‌زدن به
این فایل، درخواست‌های شبکه‌ای آن در پایین‌ترین نقطهٔ مشترک گرفته می‌شوند:

```
LoginActivity  ──TL_auth_sendCode / signIn / signUp / resendCode──►  ConnectionsManager.sendRequest
                                                                        │
                                                          (فقط برای درخواست‌های احراز هویت)
                                                                        ▼
                                                        PlatformAuthInterceptor
                                                                        │
                                          AuthManager ──► REST واقعی: /auth/otp/request, /auth/otp/verify,
                                                                  /auth/register, /auth/login, /auth/refresh
                                                                        │
                                                                        ▼
                                          پاسخ TL مصنوع: TL_auth_sentCode / TL_auth_sentCodeSuccess /
                                                          TL_auth_authorization / TL_error
```

نتیجه: **هیچ ویو، رنگ، فونت، انیمیشن یا دکمه‌ای تغییر نکرده**؛ حتی مسیر رفتن به صفحهٔ ثبت‌نام هم همان
مسیر اصلی تلگرام است، چون تبدیل «شمارهٔ ناشناس» به «صفحهٔ ثبت‌نام» از طریق همان
`TL_auth_sentCodeSuccess → TL_auth_authorizationSignUpRequired` انجام می‌شود که خودِ اپ انتظار دارد.

## ۲. نگاشت کامل عملیات TL به API

| درخواست اپ | فراخوانی واقعی | پاسخ ساخته‌شده برای UI |
|---|---|---|
| `TL_auth_sendCode(phone)` | `POST /auth/otp/request` `{username:"ph"+digits, purpose:"login"}` | `202` → `TL_auth_sentCode` (type=SMS، طول ۶، `phone_code_hash`، `timeout=expires_in`) |
| همان، حساب موجود نیست | پاسخ `404` بک‌اند | `TL_auth_sentCodeSuccess` با `TL_auth_authorizationSignUpRequired` → **صفحهٔ ثبت‌نام خودِ اپ** |
| `TL_auth_resendCode(phone)` | همان `POST /auth/otp/request` (کد قبلی باطل می‌شود) | `TL_auth_sentCode` |
| `TL_auth_signIn(phone, code)` | `POST /auth/otp/verify` → جفت توکن | `TL_auth_authorization` با `TL_user` ساخته‌شده از پاسخ واقعی `/users/me` |
| `TL_auth_signUp(phone, first, last)` | `POST /auth/register` با رمز تصادفی تولیدشده روی دستگاه | `TL_auth_authorization` |
| خطای ۴۰۱ (کد اشتباه) | توستِ بک‌اند `Incorrect code` | `TL_error(400, "PHONE_CODE_INVALID")` → همان هشدار «InvalidCode» خودِ اپ |
| ۴۲۹ (سقف تلاش) | `retry_after` | `TL_error(420, "FLOOD_WAIT_<n>")` → هشدار FloodWait خودِ اپ |
| ۴۰۳ (حساب مسدود) | `Account is blocked` | `TL_error(403, "PHONE_NUMBER_BANNED")` |
| ۴۰۹ (شماره/حساب تکراری) | `Conflict` | `TL_error(400, "PHONE_NUMBER_OCCUPIED")` |
| ۵۰۲ (ارسال کد ناموفق) | گیت‌وی SMS خطا داد | `TL_error(500, ...)` + پیام قابل‌مشاهده |
| قطع شبکه / تایم‌اوت | `IOException` در `PlatformApi` | `TL_error(-1, "NETWORK_ERROR")` |
| بدنهٔ نامعتبر (غیر JSON) | `JsonParseException` | `TL_error(500, "INTERNAL_ERROR")` |

**هویت:** شمارهٔ تلفن همان چیزی است که کاربر می‌بیند؛ `PhoneIdentity` آن را قطعی به نام‌کاربری بک‌اند
تبدیل می‌کند: `+49 151 1234 5678` → `ph4915112345678`. بدون جدول نگاشت و بدون تصادم، روی هر دستگاه.

## ۴. ذخیره و بازیابی نشست

- توکن‌ها با **AES-256-GCM** و کلید داخل **Android Keystore** ذخیره می‌شوند (کلید از سندباکس اپ خارج نمی‌شود).
- در هر بار اجرای برنامه، `ApplicationLoader` → `PlatformBridge.startSession()` → `AuthManager.restore()`:
  اگر توکن هست، ابتدا `POST /auth/refresh` (چرخش) و سپس `GET /users/me` انجام می‌شود؛ اگر ۴۰۱ برگردد
  توکن‌ها پاک و کاربر به صفحهٔ ورود برمی‌گردد.
- خروج: `POST /auth/logout` (ابطال سمت سرور) + پاک‌سازی محلی، سپس `endSession()` کش محلی را خالی می‌کند
  تا دادهٔ کاربر قبلی نماند.

## ۵. تمدید خودکار توکن

`PlatformApi` روی هر پاسخ ۴۰۱ یک‌بار `POST /auth/refresh` می‌زند؛ قفل `refreshLock` تضمین می‌کند چند
درخواست هم‌زمان فقط **یک** چرخش بسازند. سرور چرخش را یک‌بارمصرف می‌داند: استفادهٔ دوباره از refresh
قدیمی به‌عنوان «سرقت توکن» تلقی و کل نشست ابطال می‌شود (این رفتار در تست پوشش داده شده است).

## ۶. سرویس ارسال کد — وضعیت صادقانه

| مورد | وضعیت |
|---|---|
| پیاده‌سازی درگاه واقعی | ✅ سه درگاه: **Twilio**، **Kavenegar** (شماره‌های ایران)، **Webhook** عمومی |
| انتخاب با `SMS_PROVIDER` | ✅ `log` / `twilio` / `kavenegar` / `webhook` |
| اعتبارسنجی تنظیمات | ✅ اگر درگاه انتخاب شده ولی کلیدش نباشد، ساخت sender با خطا متوقف می‌شود؛ در `production` بودن `log` باعث خطای راه‌اندازی است |
| تست واقعی پروتکل | ✅ در تست‌ها هر سه درگاه روی یک **سرور HTTP واقعی محلی** صدا زده می‌شوند و بدنه/هدر/پارامترها بررسی می‌شوند (Twilio: فرم + Basic Auth، Kavenegar: query، Webhook: JSON + Bearer) |
| **ارسال واقعی پیامک در این محیط** | ❌ **انجام نشد** — هیچ کلید و شمارهٔ ارائه‌دهنده‌ای در دسترس نیست. در این محیط `SMS_PROVIDER=log` است و کد در لاگ سرور ثبت می‌شود |
| شکست ارسال | ✅ پاسخ `502` به کلاینت و باطل‌شدن کد؛ تست شده |

بنابراین: «کد آزمایشی» به‌عنوان سرویس واقعی معرفی **نمی‌شود**؛ مسیر پیامک واقعی پیاده شده اما تا وارد
کردن اعتبارنامهٔ یک ارائه‌دهنده، ارسال واقعی اثبات نشده است.

## ۸. محدودیت صریح

- **کامپایل و ساخت APK انجام نشده**: در این محیط JDK و Android SDK وجود ندارد و قابل دریافت نبود.
  اعتبارسنجی کد جاوا = پارس کامل با `javalang` + بررسی ایستای اتکا نکردن به MTProto + تضمین
  «فقط افزودن خط» در فایل‌های بالادستی + تطبیق کامل قرارداد API روی سرور واقعی. **نه اجرای بایت‌کد.**
- **صفحهٔ اصلی پس از ورود خالی است**: احراز هویت و نشست کامل کار می‌کند، اما دادهٔ صفحهٔ اصلی
  (دیالوگ‌ها، پیام‌ها) در فازهای ۳ و ۴ از `ChatRepository`/`MessageRepository` تأمین می‌شود؛
  تا آن زمان اپ همان مسیر دادهٔ قدیمی را دارد.
- **متن خطای شبکه**: بک‌اند پیام فارسی ندارد؛ در خطای شبکه رشتهٔ `NETWORK_ERROR` به همان مسیر
  هشدار خود اپ می‌رسد. افزودن رشتهٔ ترجمه‌شده یک تغییر متنی است، نه طراحی، و در فاز بعد انجام می‌شود.
- **صفحهٔ «دستگاه‌های فعال» اپ** (ActiveSessions) هنوز به لیست نشست‌های ما وصل نشده؛ سطح API
  (`GET/DELETE /auth/sessions`) آماده و تست‌شده است، اما ویو آن صفحه در نسخهٔ فعلی از کلاس‌های TL
  مخصوص دستگاه استفاده می‌کند که در این فورک وجود ندارند.

## ۸.۵ مرحلهٔ اعتبارسنجی واقعی (این دور)

### تلاش برای کامپایل واقعی

| مسیر | نتیجه |
|---|---|
| نصب JDK/SDK در سندباکس | ❌ غیرممکن — تنها JRE بدون `javac` قابل دریافت بود (PyPI)، و مخازن Maven/Google (`dl.google.com`, `repo1.maven.org`) هم در دسترس نیستند |
| GitHub Actions برای این برنچ | ⚠️ **workflow نوشته و کامیت شد ولی اجرا نشد**: توکن این محیط مجوز `actions:write` ندارد (`HTTP 403` روی dispatch) و push های آن رویداد workflow ایجاد نمی‌کنند |
| آماده‌سازی برای اجرا | ✅ `.github/workflows/build-apk.yml` (همان مسیری که قبلاً در این ریپو موفق به ساخت APK شده) با سه job: `compile` / `apk` / `emulator` |

**برای اجرا:** Actions → «Build Telegram APK» → Run workflow → شاخهٔ `arena/76249c66-telegram`.
job اول در چند دقیقه کامپایل جاوا را مشخص می‌کند، job دوم APK می‌سازد و job سوم بک‌اند و اپ را روی
امولاتور بالا می‌آورد و لاگ‌کت و اسکرین‌شات را artifact می‌کند.

### ابزار جدید: بررسی سازگاری TL (جای کامپایلر)

`tools/check_tl_contract.py` خودِ `TLRPC.java` را پارس می‌کند (۲٬۲۶۸ کلاس) و هر فیلد/متدی که آداپتور
استفاده می‌کند را با تعریف واقعی مقایسه می‌کند. **اولین اجرا یک خطای کامپایل واقعی پیدا کرد:**

```
DtoMapper.java: TL_userStatusOffline.was_online is not a field of that TL class
```

در این فورک، `TL_userStatusOffline` تنها `expires` دارد (فیلد در کلاس پایهٔ `UserStatus`)، پس
`status.was_online = ...` هرگز کامپایل نمی‌شد. اصلاح شد به `status.expires = ...`.
اکنون: **۵۲ انتساب فیلد TL و ۷ فراخوانی متد پلتفرم، همه معتبر**.

### اثبات مالکیت شماره پیش از ثبت‌نام (بند ۸)

پیش از این، `POST /auth/register` بدون هیچ اثباتی حساب می‌ساخت. اکنون:

1. `POST /auth/otp/request` با `purpose=register` برای شمارهٔ بدون حساب، کد را **واقعاً ارسال** می‌کند
   و یک `registration_token` یک‌بارمصرف برمی‌گرداند (جدول `registration_grants`، انقضا = انقضای کد).
2. `POST /auth/register` بدون توکن معتبر → **۴۰۳** «Phone number is not verified».
3. توکن به همان شماره قفل است، یک‌بارمصرف است، با انقضا باطل می‌شود، و کد مصرف‌شده دیگر برای ورود
   قابل استفاده نیست.
4. آداپتور اندروید همین مسیر را طی می‌کند: `sendCode` برای شمارهٔ ناشناس، کد ثبت‌نام می‌گیرد و
   توکن را نگه می‌دارد؛ `signUp` آن را می‌فرستد؛ اگر توکن نبود/منقضی شد، خطای `PHONE_CODE_EXPIRED`
   به UI می‌رسد و کاربر به صفحهٔ شماره برمی‌گردد (بدون هیچ تغییر ظاهری).

۶ تست جدید این مسیر را پوشش می‌دهد (بدون توکن، یک‌بارمصرف، قفل‌شده به شماره، ارسال ناموفق، انقضا،
مصرف کد).

## ۹. معیار پایان فاز ۲ — ارزیابی

| معیار | وضعیت |
|---|---|
| ثبت‌نام از طریق اپ | ✅ منطق کامل و آزمایش‌شده در سطح قرارداد (فرم ثبت‌نام همان فرم اصلی) |
| ورود به حساب | ✅ |
| ذخیرهٔ نشست | ✅ Keystore + تست بازیابی |
| باقی‌ماندن ورود پس از اجرای مجدد | ✅ در سطح منطق کلاینت (`AuthManager.restore`) و سرور |
| بدون Mock/دادهٔ ساختگی | ✅ همهٔ درخواست‌ها به بک‌اند واقعی |
| ظاهر بدون تغییر | ✅ صفر خط حذف‌شده در فایل‌های UI؛ هیچ فایل UI ویرایش نشد |

آنچه هنوز **قابل اثبات با اجرای اپ نیست**: اینکه روی گوشی/شبیه‌ساز همین رفتار دیده شود، چون ساخت
APK در این محیط ممکن نیست. این تنها شکاف باقی‌ماندهٔ فاز ۲ است و با یک محیط دارای Android SDK
قابل بستن است.
