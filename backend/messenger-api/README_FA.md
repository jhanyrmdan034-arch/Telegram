# API نمونهٔ پیام‌رسان مستقل

این سرویس یک نمونهٔ محدود برای ورود آزمایشی با شماره، پروفایل، گفت‌وگوی دونفره و پیام متنی پایدار است. لایهٔ دادهٔ Android اکنون از REST/SSE به این سرویس وصل می‌شود و UI برنامه تغییر نکرده است؛ APK هنوز در CI کامپایل و روی emulator تأیید نشده است.

## پیش‌نیاز و راه‌اندازی محلی

- Node.js نسخهٔ 22.5 یا جدیدتر (برای ماژول داخلی SQLite)
- هیچ بستهٔ npm خارجی لازم نیست.

از این پوشه اجرا کنید:

```sh
npm test
npm run seed:demo
MESSENGER_HOST=127.0.0.1 MESSENGER_PORT=8080 \
MESSENGER_DB_PATH="$PWD/.data/messenger.sqlite" npm start
```

سرویس به‌طور پیش‌فرض فقط روی loopback گوش می‌دهد و فایل دیتابیس را در `.data/messenger.sqlite` با WAL و Foreign Key فعال می‌سازد. برای شبکهٔ غیر loopback باید `MESSENGER_ALLOW_REMOTE=1` را صریحاً تنظیم کرد؛ پیش از آن TLS reverse proxy، firewall و سیاست نشست production الزامی است. هیچ راز یا رمز عبوری در مخزن نیست.

## احراز هویت آزمایشی

`POST /api/v1/auth/phone` شمارهٔ E.164 می‌گیرد. اگر وجود نداشته باشد حساب ایجاد می‌شود؛ در غیر این صورت نشست جدید برای همان حساب می‌سازد. هیچ OTP، SMS یا رمز عبوری وجود ندارد. Bearer token تصادفی 256-bit فقط یک‌بار در پاسخ برمی‌گردد و در SQLite صرفاً SHA-256 آن ذخیره می‌شود. این مدل **احراز هویت نیست**: هرکس شماره‌ای را وارد کند می‌تواند به حساب آن شماره وارد شود. فقط برای محیط آزمایشی کنترل‌شده است و برای هاست عمومی ممنوع است.

## API نسخهٔ ۱

تمام endpointها به‌جز `/health` و `POST /api/v1/auth/phone` به `Authorization: Bearer <token>` نیاز دارند.

- `POST /api/v1/auth/phone` — body: `{ "phone": "+999000000001" }`
- `GET /api/v1/me` — پروفایل حساب فعلی
- `PATCH /api/v1/me` — `firstName`, `lastName`, `username`, `bio`
- `GET /api/v1/users/{id}` — پروفایل عمومی، بدون شمارهٔ تلفن
- `GET /api/v1/users/search?q=...&limit=20` — جست‌وجوی نام/نام‌کاربری/شماره برای پیدا کردن کاربر؛ شماره در پاسخ عمومی نمی‌آید
- `POST /api/v1/conversations/direct` — body: `{ "peerUserId": 2 }`
- `GET /api/v1/conversations` — فهرست گفت‌وگوهای حساب
- `GET /api/v1/conversations/{id}/messages?limit=50&before={messageId}`
- `POST /api/v1/conversations/{id}/messages` — body: `{ "text": "..." }`
- `GET /api/v1/events` — SSE سطح حساب، شامل پیام گفت‌وگوی تازه‌ای که هنوز در فهرست دستگاه نیست؛ replay با `Last-Event-ID`
- `GET /api/v1/conversations/{id}/events` — رویدادهای SSE همان گفت‌وگو، با تطبیق مجدد history پس از اتصال
- `DELETE /api/v1/auth/session` — لغو نشست جاری
- `GET /health` — بررسی زنده‌بودن و quick-check دیتابیس

تمام درخواست‌ها اعتبارسنجی می‌شوند؛ بدنهٔ JSON حداکثر 64 KiB و پیام متنی حداکثر 4096 نویسه است. دسترسی به گفت‌وگو با membership کنترل می‌شود. خطاهای سرور جزئیات داخلی SQLite را به کلاینت نشت نمی‌دهند.

## دو حساب آزمایشی

`npm run seed:demo` دو شمارهٔ ساختگیِ آزمایشگاهی (`+999000000001`, `+999000000002`) را در دیتابیس محلی ایجاد می‌کند، گفت‌وگوی دونفره می‌سازد و یک پیام اولیه ثبت می‌کند. شماره‌ها فقط fixture هستند، OTP/رمز ندارند و نباید برای انتشار یا دادهٔ واقعی استفاده شوند. تست یکپارچه نیز ورود دو حساب، ویرایش پروفایل، جست‌وجو، ارسال/دریافت پیام، SSE گفت‌وگو و SSE سطح حساب برای اولین پیام در گفت‌وگوی تازه، replay رویداد و ماندگاری پس از بازشدن مجدد دیتابیس را روی دیتابیس موقت آزمایش می‌کند.

## محدوده و محدودیت

تست‌های HTTP رفتار backend را اثبات می‌کنند؛ build و آزمون emulator برنامه هنوز باید از workflow جداگانه اجرا شود. برای debug، URL پیش‌فرض Android برابر `http://10.0.2.2:8080` است؛ build release فقط HTTPS را می‌پذیرد و باید با `MESSENGER_API_BASE_URL` تنظیم شود. SQLite برای این نسخهٔ تک‌نمونه‌ای و آزمایش پایدار است، نه جایگزین PostgreSQL در استقرار چندنمونه‌ای/تولیدی. هنوز upload رسانه، پیام گروهی، delivery/read receipt، push، پنل مدیریت، محدودسازی درخواست، سیاست OTP و TLS خود سرویس پیاده نشده است. ورود بدون OTP و بدون password باید قبل از هر دسترسی عمومی با OTP/محدودسازی و بازیابی امن حساب جایگزین شود.
