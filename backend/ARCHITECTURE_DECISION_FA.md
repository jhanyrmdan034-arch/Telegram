# تصمیم معماری نسخهٔ آزمایشی مستقل

**وضعیت:** REST نسخه‌بندی‌شده و SSE برای نمونهٔ عمودی انتخاب و تا حد اصلی به Android adapter متصل شده؛ بازبینی نهایی پس از build و آزمون emulator لازم است.

## واقعیت‌های سورس فعلی

- رابط کاربری و مدل‌های اصلی به `TLRPC`، اشیای TL تولیدشده و `MessagesController`/`MessagesStorage` وابستگی مستقیم دارند.
- ارسال درخواست Android از `ConnectionsManager` به `native_sendRequest` می‌رود؛ بنابراین شبکه صرفاً یک فراخوانی HTTP قابل تعویض نیست.
- Gateway موجود فقط framing/handshake و چند پاسخ پایه را پوشش می‌دهد؛ آن را نباید سرور سازگار با کلاینت یا بک‌اند محصول حساب کرد.

## مقایسهٔ مسیرها

| معیار | ادامهٔ MTProto و پیاده‌سازی TL در سرور | REST نسخه‌بندی‌شده + کانال رویداد |
|---|---|---|
| حفظ صفحات و مدل‌های UI | بیشترین سازگاری در کوتاه‌مدت؛ UI همچنان درخواست‌های TL خود را می‌فرستد | ظاهر دست‌نخورده می‌ماند، اما باید Adapter/Repository اندرویدی TL/REST را به مدل‌ها و رویدادهای موجود وصل کند |
| هزینهٔ سرور | بسیار بالا: handshake، کلیدها، TL Layer 232، updates, sequence/pts, dialogs, peers و semantics هر متد | کمتر و قابل پیش‌بینی‌تر: قراردادهای JSON محدود به نیاز محصول و ذخیره‌سازی مستقیم |
| ریسک امنیتی | بالا؛ خطای رمزنگاری/هم‌زمانی یا پاسخ ناسازگار می‌تواند کلاینت را قطع یا وضعیت محلی را خراب کند | متوسط؛ سطح حملهٔ HTTP معمول است و قابل پوشش با TLS، token، validation و rate limit است |
| استقلال از Telegram | از نظر اتصال ممکن است، اما مدل و قراردادهای Telegram باقی می‌مانند | استقلال واقعی پروتکل و مالکیت قراردادها |
| قابلیت‌های آتی | فقط با پیاده‌سازی هر خانوادهٔ TL و رفتارهای مرتبط؛ نگهداری نسخه‌های لایه پرهزینه است | افزودن قابلیت‌ها به قراردادهای خود پروژه و migrationهای خود پروژه ساده‌تر است |
| هزینهٔ Android | کم برای سازگاری خام؛ زیاد برای سروری که واقعاً همهٔ رفتارهای TL را تقلید کند | زیاد در آغاز برای Adapter و اتصال مدل‌های موجود؛ پس از آن وابستگی به TL کم می‌شود |

## انتخاب

برای بک‌اند محصول، **REST نسخه‌بندی‌شده با نشست bearer و رویدادهای سروری** انتخاب می‌شود. UI/XML/رنگ/چیدمان صفحات حفظ می‌شوند؛ تغییرات مجاز به کد شبکه و سازگارساز داده محدود خواهند بود. Gateway موجود در `mtproto-gateway` به‌عنوان آزمایش پروتکل ایزوله باقی می‌ماند و مبنای پیاده‌سازی قابلیت‌های محصول نخواهد بود.

برای این گام دامنه به این عمود محدود است: ورود آزمایشی با شماره بدون OTP (به‌صراحت ناامن و فقط محلی/آزمایشی)، پروفایل، گفت‌وگوی دونفره و پیام متنی پایدار. ذخیره‌سازی آزمایشی SQLite فایل‌محور است تا بدون سرویس خارجی، ایجاد/بازیابی واقعی داده و تست دو حساب انجام شود. این انتخاب جایگزین PostgreSQL برای استقرار چندنمونه‌ای یا بار تولیدی نیست؛ مهاجرت PostgreSQL باید پیش از محصول عمومی انجام شود.

## هزینه و ریسک باقی‌مانده

1. Adapter اصلی (ورود، پروفایل، جست‌وجو، گفت‌وگو، history، پیام و SSE) نوشته شده، اما هنوز با Gradle کامپایل یا روی emulator تأیید نشده است؛ workflow جداگانهٔ debug و instrumentation برای این کار آماده شده است.
2. حذف کامل مسیر MTProto از کلاینت در این نسخه هدف نیست؛ امکانات خارج از محدوده هنوز به مسیر قدیمی وابسته‌اند و نباید backend مستقل‌شده برای کل برنامه معرفی شوند.
3. ورود بدون OTP هیچ تضمین هویتی ندارد. فقط برای دو حساب آزمایشی loopback/محیط کنترل‌شده؛ انتشار عمومی ممنوع.
4. build محلی به‌علت نبود JDK/Android SDK ممکن نیست؛ باید از CI با JDK 17، Android SDK API 36، NDK 27.2.12479018 و dependencyهای پروژه اجرا و تأیید شود.
